You are a senior full-stack engineer, audio/ML integration engineer, UI/UX designer, and QA engineer.

2. PRODUCT VISION

Vox Shift is a real-time, bidirectional speech translation and dubbing application.

Its primary purpose is to let users communicate naturally across languages without needing to speak the other person's language.

The product must support two independent translation directions:

Direction A — User speaks Persian

Persian speech
→ Streaming speech recognition
→ Natural English translation
→ English speech generated using the user's configured voice identity
→ Audio playback

Direction B — Other person speaks English

English speech
→ Streaming speech recognition
→ Natural Persian translation
→ Persian speech generated using the selected output voice
→ Audio playback

The application must preserve conversation context, speaker attribution, saved settings, and conversation history.

The primary initial language pair is Persian ↔ English.

The architecture must support additional languages without requiring a complete rewrite.

The product should eventually support video dubbing, but video dubbing is not a release-blocking requirement for Version 1.0.0.

Product priorities

1. Functional and genuinely integrated voice identity.
2. Natural, accurate, conversational speech translation.
3. Reliable bidirectional conversation handling.
4. Persistent user settings and voice profiles.
5. Persistent sessions and searchable conversation threads.
6. Low latency and stable audio playback.
7. A polished, redesigned, responsive user interface.
8. Reliable deployment, configuration, and testing.

Do not sacrifice core functionality to create decorative UI elements.

5. VOICE IDENTITY — FUNCTIONAL IMPLEMENTATION

Voice identity is one of the core differentiators of Vox Shift.

The current behavior is unacceptable if recording a user's voice does not change the generated audio.

Do not implement a cosmetic voice identity feature.

5.1 Investigate and fix the existing voice pipeline

Trace this complete sequence:

Record sample
→ Upload sample
→ Validate sample
→ Create or enroll voice profile
→ Store provider profile identifier
→ Save local application profile
→ Select the saved profile
→ Submit translated text or audio to the actual voice provider
→ Generate audio using that profile
→ Play generated audio
→ Verify the generated voice is associated with the selected profile.

Every stage must be connected to the next stage.

The generated audio must not silently fall back to the default demo voice when a custom profile is selected.

If fallback is explicitly offered, show a warning and identify the actual voice being used.

5.2 Voice enrollment workflow

Create a dedicated Voice Identity page with:

- Record Voice Sample.
- Upload a permitted audio sample, if supported.
- Recording duration and audio-quality feedback.
- Sample validation.
- Background noise and clipping warnings where measurable.
- Voice enrollment progress.
- Current processing stage.
- Estimated remaining time when a defensible estimate exists.
- Retry and cancel actions.
- Test My Voice.
- Save Profile.
- Rename Profile.
- Set as Default.
- Delete Profile.

Support multiple profiles where the chosen provider and architecture permit it.

Allow the user to record a sample once, save the resulting profile, and reuse it across future sessions.

Do not require the user to repeat voice enrollment whenever they open a new thread.

5.3 Genuine voice similarity

Research and evaluate reputable voice providers and recognition/voice-processing technologies using their official documentation.

Compare available capabilities, including:

- Reference-audio-based voice cloning.
- Persistent speaker or voice IDs.
- Cross-language voice cloning.
- Multilingual text-to-speech.
- Voice conversion where appropriate.
- Streaming or low-latency generation.
- Sample-duration and audio-quality requirements.
- Voice enrollment time.
- Pricing, quotas, regional availability, and licensing.

Select a provider based on actual requirements and testable performance, not marketing claims.

Keep the provider integration modular so it can be replaced later.

Do not confuse speaker recognition, speaker embeddings, voice similarity analysis, voice cloning, and ordinary text-to-speech. These solve different problems.

If the current provider only selects the closest preset voice, it does not satisfy the custom voice identity requirement.

Replace or extend that implementation with a provider that supports the required capability.

Do not invent support for voice cloning or claim that a generic preset voice is the user's cloned voice.

Use only voice samples the user is authorized to provide, and make sample handling and deletion behavior explicit.

5.4 Voice identity progress indicator

Implement a real enrollment progress interface.

Display:

- Overall progress percentage.
- Current processing stage.
- Elapsed time.
- Estimated remaining time, when available.
- Completion or failure status.

Possible stages:

1. Waiting for recording.
2. Recording sample.
3. Uploading audio.
4. Validating sample.
5. Creating voice profile.
6. Provider confirmation.
7. Saving profile.
8. Testing generated speech.
9. Ready to use.

Progress must reflect actual backend or provider job status whenever possible.

If the provider supplies only asynchronous completion, use genuine job-state polling or supported callbacks.

Do not fabricate a precise percentage or countdown.

If exact progress cannot be measured, display an honest indeterminate progress indicator, the current stage, elapsed time, and an estimate only when historical measurements support it.

For example:

"Analyzing voice sample…"
"Stage 4 of 7"
"Elapsed: 12 seconds"
"Estimated remaining: unavailable"

Once enrollment finishes, display a clear Ready status and provide a real audio test.

5.5 Verify that custom voices actually work

Create an end-to-end test that:

1. Creates or selects a custom voice profile.
2. Generates speech using a fixed test sentence.
3. Confirms the selected profile ID is sent to the correct provider.
4. Confirms that the returned audio belongs to the generated request.
5. Verifies that switching profiles changes the selected generation configuration.
6. Confirms that errors are visible instead of silently returning the demo voice.

Where possible, provide a side-by-side comparison between the default voice and the custom voice.

Voice similarity should be evaluated using appropriate objective or perceptual methods. Do not claim an exact cloning percentage unless a validated metric and methodology support that claim.

7. GLOBAL DEFAULTS AND THREAD-SPECIFIC OVERRIDES

Implement two levels of configuration.

Global defaults

The user's preferred configuration should apply automatically to all new sessions.

Examples:

- Default source and target languages.
- Default voice identity.
- Default content style.
- Default playback speed.
- Default translation provider.
- Default voice provider.
- Relevant audio preferences.

The user must not have to configure their voice identity every time they start a conversation.

Per-thread settings

Every thread must support its own settings panel.

A thread may override:

- Source language.
- Target language.
- Translation direction.
- Voice profile.
- Voice generation settings supported by the provider.
- Content style.
- Playback speed.
- Context behavior.

Use inheritance from global defaults.

If a thread has no override, use the current global default according to a documented and consistent policy.

Once a thread-specific override is explicitly saved, preserve it when reopening that thread.

Make it easy to:

- View inherited settings.
- Change settings for the current thread only.
- Reset thread settings to global defaults.
- Save a new default globally when explicitly requested.

Do not unexpectedly overwrite thread-specific settings when global defaults change.

Persist voice profile references rather than repeatedly uploading or re-enrolling the same voice sample.

8. SESSIONS AND THREADS — PERSISTENT CONVERSATION HISTORY

Build a complete Sessions and Threads system.

This is a core Version 1.0.0 requirement, not a future placeholder.

Use a consistent data model that separates a conversation thread from an individual live session.

A thread represents a continuing conversation.

A session represents a recording or live interaction within that thread.

A thread may contain multiple sessions, including sessions created on different days.

8.1 Sessions page

Create a polished conversation history page.

Each thread should display, where available:

- Conversation title.
- Participants or speaker labels.
- Language pair.
- Last activity.
- Creation date.
- Number of sessions.
- Message or utterance count.
- Saved transcript status.
- Voice configuration indicator.

Provide:

- Search.
- Sort by recent activity.
- Filters by language pair.
- New Conversation.
- Open Conversation.
- Rename.
- Delete with confirmation.
- Continue Conversation.

Support an empty state with a clear New Conversation action.

8.2 Thread detail page

When a user opens a previous thread, show its complete chronological conversation history.

Each utterance should retain, where available:

- Original recognized text.
- Translated text.
- Source language.
- Target language.
- Speaker identity or label.
- Timestamp.
- Session ID.
- Translation direction.
- Voice profile used.
- Audio reference, if retained.
- Processing status or error information.

Display the original and translated text clearly.

For example:

Speaker A — Persian:
"سلام، جلسه رو شروع کنیم."

Translation — English:
"Hi, let's start the meeting."

Speaker B — English:
"Sure, let's begin."

Translation — Persian:
"حتماً، شروع کنیم."

Provide playback controls when audio has been retained.

Do not pretend that audio is available when only the transcript was saved.

8.3 Continue an old conversation

A user must be able to reopen a thread from several days or weeks earlier and continue the same conversation.

The workflow must be:

1. Open Sessions.
2. Select an existing thread.
3. Read its previous transcript.
4. Review the thread's settings and voice profile.
5. Press Start or Resume.
6. Begin a new live session inside the existing thread.
7. Continue bidirectional translation.
8. Save new utterances and audio references.
9. Update the thread's last activity.

Do not create a duplicate thread when the user intends to continue an existing one.

Each resumed interaction should have a distinct session ID, while remaining part of the original thread.

Restore the thread's settings and relevant conversation context.

Do not assume that browser memory alone is sufficient for persistence.

8.4 New conversation

When the user selects New Conversation:

- Create a new thread.
- Apply the current global defaults.
- Allow thread-specific configuration.
- Initialize a new session when recording begins.
- Save utterances as they are finalized.
- Preserve completed utterances if the live connection fails.

9. BIDIRECTIONAL LIVE TRANSLATION

Implement both directions using a shared, configurable pipeline.

Direction A: Persian to English

Microphone
→ Streaming ASR
→ Persian transcript
→ Context-aware translation
→ English text
→ Selected voice generation
→ Audio playback

Direction B: English to Persian

Incoming microphone or supported audio input
→ Streaming ASR
→ English transcript
→ Context-aware translation
→ Persian text
→ Selected target voice generation
→ Audio playback

Do not implement reverse translation as a cosmetic language-selector change.

Verify that the correct source language, target language, voice profile, and translation pipeline are used.

Speaker handling

For live two-person conversations, support reliable source separation at the application level through appropriate input selection or supported speaker attribution.

If both speakers use one microphone, use diarization only when supported by the selected service and the audio quality makes it feasible.

Do not assume that a single microphone can always identify speakers perfectly.

Where separate microphone or channel input is required, explain this limitation in the UI.

Prevent translated playback from being accidentally recognized again as new source speech whenever possible.

Evaluate headphone playback, echo cancellation, noise suppression, voice activity detection, and playback interruption behavior.

Live behavior

- Support partial transcription when available.
- Finalize utterances using appropriate endpointing or voice activity detection.
- Avoid generating duplicate translations.
- Preserve utterance order.
- Handle temporary disconnections.
- Provide retry behavior where safe.
- Avoid silently losing completed utterances.
- Keep the UI responsive while processing occurs.

Do not block the main UI while awaiting audio generation.

10. AUDIO QUALITY, LATENCY, AND RELIABILITY

Keep microphone capture, speech recognition, translation, voice generation, and audio output modular.

Evaluate the available realtime transport options, including WebRTC and WebSocket streaming, against the existing stack and provider capabilities.

Measure actual performance.

Track:

- Audio capture and buffering.
- ASR latency.
- Translation latency.
- Voice generation latency.
- Time to first playable audio.
- End-to-end latency.
- Failed requests.
- Rate-limit events.
- Reconnection attempts.

Report actual measured values rather than invented estimates.

Preserve the original meaning and conversational tone while minimizing unnecessary delays.

Prioritize understandable, natural speech over aggressive optimizations that damage audio quality.

Use chunked playback only if it improves the real implementation and maintains acceptable speech continuity.

Do not assume that a provider supports streaming generation without verifying its current official documentation.

11. CONTENT STYLE AND TRANSLATION CONTEXT

Provide at least these styles:

Natural: Conversational translation that preserves meaning, intent, and tone.

Literal: Translation that stays closer to the original wording.

Clean: Translation that follows a clearly defined content-filtering policy without silently changing the speaker's intent.

Natural should be the default.

Maintain relevant thread context so that names, terminology, pronouns, and ongoing topics remain consistent.

Use appropriate technical, professional, and casual language according to context.

Allow the user to control context retention through settings.

Avoid sending the entire conversation repeatedly if a compact context summary or bounded context window can accomplish the same purpose.
